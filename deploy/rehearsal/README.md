# Репетиция переезда Прагматики на v2

Пакет проверяет на РФ-сервере, рядом с боем, что боевые данные ложатся на v2: БД
восстанавливается и мигрирует, хранилище псевдонимизатора читается, приложение стартует и
отвечает `/ready`. **Бой репетиция не меняет**: боевые контейнеры, тома и `/opt/pragmatika`
только читаются, всё остальное живёт в отдельном compose-проекте `pragmatika-rehearsal`
(свои контейнеры, тома и сеть, без опубликованных портов).

Режим **лёгкий**: `postgres`, `migrate`, `pseudonymizer`, `app` без каналов и заглушка шлюза
моделей. Полный второй стек (сумма `mem_limit` боя около 13 ГиБ) на этом хосте не поднимается.
Если ресурсов не хватает даже на лёгкий режим, скрипт отказывается (код 3) до создания чего-либо.

## Состав пакета

| Файл | Назначение |
|------|------------|
| `rehearse.sh` | сценарий репетиции |
| `images.lock` | образы по digest (платформа 1.0.x и app проекта) |
| `cosign.pub` | открытый ключ проверки подписей образов |
| `schema-expected.sql` | нормализованная схема чистой БД v2 |
| `expected-pending.txt` | миграции, которые должны ожидать на схеме боя |
| `expected-env-names.txt` | имена боевого окружения по архиву сбора (если есть) |
| `tools/check_migrations_schema.py` | сравнение схем |
| `stack/` | compose, миграции и платформенная копия (без секретов) |
| `MANIFEST.sha256` | контрольные суммы файлов пакета |

## Что нужно на сервере

- Docker и Compose 2.24 или новее (на бою 2.40.3), `python3`, `tar`, `sha256sum`, `flock`.
- Пользователь с доступом к docker и на чтение `/opt/pragmatika/deploy/.env`,
  `/etc/pragmatika` (включая `secrets/`) и `/opt/pragmatika/local`.
- Свободно: не меньше 3 ГиБ доступной памяти и места на диске втрое больше размера БД (не менее
  6 ГиБ) в домашнем каталоге и в каталоге данных docker. Пороги можно изменить переменными
  `REHEARSAL_MIN_AVAILABLE_MIB` и `REHEARSAL_MIN_DISK_MIB`, но снижать их не нужно: именно на
  нехватке памяти RU-ВМ репетиция должна отказать, а не уронить бой.
- Доступ к образам из `images.lock`: `docker login` в реестр ключом на чтение либо загрузка из
  архива `--images-tar`. Ключ давайте во временный `DOCKER_CONFIG`, после запуска выполните
  `docker logout`.

## Как перенести и запустить

```bash
# На машине сборки: проверить целостность и передать каталог пакета.
(cd package && sha256sum -c --quiet MANIFEST.sha256)
scp -r package/ <пользователь>@<сервер>:~/pragmatika-rehearsal-package/

# На сервере:
cd ~/pragmatika-rehearsal-package
(sha256sum -c --quiet MANIFEST.sha256)
bash rehearse.sh --preflight-only     # только предусловия, ничего не создаёт
bash rehearse.sh                      # полная репетиция
```

Параметры: `--lock ФАЙЛ`, `--images-tar ФАЙЛ`, `--out-dir КАТАЛОГ` (куда класть итоговый архив,
по умолчанию `$HOME`), `--backup-sh` (вызвать штатный `backup.sh` боя: он пишет архив и, как ночной запуск, грузит его
в S3; без флага репетиция боя НЕ пишет и бэкапа не делает), `--age-identity ФАЙЛ` (см. ниже), `--battle-config ФАЙЛ` (переопределения `BATTLE_*`, если
боевой стек называется иначе, чем `pragmatika`), `--keep` (не убирать стек: только для отладки).

Что репетиция делает, по шагам:

1. Предусловия: память, диск, Compose, образы по digest, подпись образа app (`cosign verify`,
   если `cosign` есть). Снимок боевых контейнеров (id, состояние, время старта).
2. Только с `--backup-sh`: свежий бэкап боя штатным `deploy/scripts/backup.sh` в
   `~/backups/rehearsal-<время>/`. Без флага шаг пропускается (проверка `warn`).
3. Рабочий дамп БД: `pg_dump` с чтением из боевого контейнера либо, если дан закрытый ключ age,
   распаковка только что снятого архива бэкапа.
4. Восстановление в Postgres репетиции, `migrate --plan` (ожидающие миграции сверяются с
   `expected-pending.txt`), применение, повторный `--plan`, `pg_dump --schema-only` и сравнение
   со `schema-expected.sql`.
5. Копия тома `pragmatika_pseudonymizer-data` (боевой том смонтирован `:ro`, копия снимается
   средствами SQLite), самопроверка хранилища без вывода значений, старт псевдонимизатора v2,
   проверка маскирования и восстановления на выдуманном тексте.
6. Старт `app` с пустыми `BITRIX24_*` и заглушкой шлюза моделей: `/ready`, журнал без ошибок
   конфигурации, 4 агента в реестре (`prices`, `documents`, `order-calc`, `site-export`).
7. Пики памяти контейнеров против `mem_limit`.
8. Уборка: остановка и удаление проекта репетиции, его томов, рабочих копий дампа и настроек.
9. Сверка: боевые контейнеры не изменились.

Проверки имён: имена томов боя должны существовать в compose v2; имена переменных боевого
окружения сверяются с `expected-env-names.txt` и с compose v2 (`env-names.json` в результатах).
`/etc/pragmatika` переносится целиком в рабочую копию (`mail/mailboxes.json` читается только
для проверки формы, логины в репетицию не попадают).

## Что делает бой, а что читается

- **Бой не пишется по умолчанию.** Единственная запись в сторону боя - штатный `backup.sh` с явным
  `--backup-sh`: он пишет архив бэкапа и, как ночной запуск, загружает его в S3, если в боевом `.env`
  заданы `BACKUP_S3_*`. Перед переключением бэкап нужен: снимите его отдельно или повторите
  репетицию с `--backup-sh`.
- **Читается**: БД через `pg_dump` и `psql` в боевом контейнере, том хранилища псевдонимизатора
  (`:ro`), `/etc/pragmatika`, `/opt/pragmatika/local`, `deploy/.env`. `deploy/.env.bak-*` в
  репетицию не берутся.
- Все обращения к бою пишутся в `battle-calls.log` внутри архива результатов.

## Что вернуть

Файл `~/rehearsal-<время>.tgz` (или в `--out-dir`). В нём: журнал, `summary.md` с итогами проверок,
`checks.tsv`, план миграций, diff схем, пики памяти, список имён env, самопроверка хранилища,
версии. **Данных БД в архиве нет**, секреты репетиции проверяются на утечку перед упаковкой;
если значение найдено, архив не создаётся.

Как читать `summary.md`: `ok` — проверка прошла; `warn` — не провал, но требует решения владельца
(например, имена env боя, неизвестные compose v2; события `error` в журнале app; подпись образа не
проверена, потому что нет входа в реестр); `fail` — провал, итоговый код 1. App в репетиции
исполняет очередь заданий из восстановленной копии БД на заглушках каналов и без выхода в сеть,
поэтому события `job_failed` в журнале возможны и сами по себе не означают ошибку v2: их коды
видны в `app-log-events.tsv`. Если у `docker` свой `DOCKER_CONFIG`, плагин `compose` из
`~/.docker/cli-plugins` ему не виден: либо вход в реестр делайте до запуска и без смены каталога
конфигурации, либо загружайте образы через `--images-tar`.

Коды выхода: 0 — все проверки прошли; 1 — есть проваленные проверки (архив создан); 2 — неверный
вызов; 3 — отказ по предусловиям (бой не тронут); 4 — сбой хода репетиции.

## Бэкап

По умолчанию репетиция бэкап НЕ снимает и в S3 ничего не пишет. Бэкап - только с явным
`--backup-sh`: тогда он лежит в `~/backups/rehearsal-<время>/` (и там, куда пишет `backup.sh` по
боевому `.env`) и остаётся: это страховка перед переключением. Архив зашифрован age; закрытый
ключ хранится офлайн у владельца и **на сервер не кладётся**. Репетиция без `--age-identity`
берёт рабочий дамп через `pg_dump`, ключ ей не нужен.

## Если репетиция прервалась или после неё

Каталоги `~/.pragmatika-rehearsal/run-*` после успешного запуска хранят только `results/` (журнал
и проверки без данных); копии настроек и дампа из них убираются.

Рабочие копии лежат в `~/.pragmatika-rehearsal/run-<время>/` (права 700). Остатки проекта:

```bash
docker compose -p pragmatika-rehearsal down -v
```

Затем удалите каталог запуска `~/.pragmatika-rehearsal/run-<время>` (вручную, он содержит копии
настроек). Повторный запуск при существующем проекте `pragmatika-rehearsal` отказывается.
Только один запуск одновременно (блокировка `~/.pragmatika-rehearsal/lock`).

## Ограничения лёгкого режима

- Каналы (Bitrix24, почта, Telegram), реальный шлюз моделей и мониторинг не проверяются: на их
  месте пустые переменные и заглушка. Проверка каналов — отдельный шаг при переключении.
- Пики памяти Postgres на копии не равны боевым (другой объём кэша, нет рабочей нагрузки).
- `indexer`, `embeddings`, `documents`, `sandbox` и остальные сервисы полного стека не
  поднимаются; про возраст их образов на бою репетиция ничего не говорит.

## Для переключения (этап 8): юниты systemd

Платформа 1.0.1 даёт `deploy/scripts/bai-units.sh` (`switch`, `revert`, `status`): он переводит
drop-in'ом на установленную платформу ровно три юнита - `stack`, `backup`, `backup-verify`.
Скрипты переключения (`cutover.sh` и `rollback.sh`) вызывают именно `bai-units.sh switch` и
`bai-units.sh revert`; репетиция юниты не трогает. Остальные юниты (`healthwatch`, `maintenance`,
`cert-expiry`, `telemetry-probe`, `container-metrics`) тоже ссылаются на старое дерево
`/opt/pragmatika` и перед его удалением требуют правки путей. Репетиция только читает их
(`systemctl cat`) и пишет `units-old-tree.tsv` (юнит, кто переводит, число ссылок на старое дерево)
для чек-листа этапа 8. Строка чек-листа: «после `bai update` выполнен `bai-units.sh switch`,
`bai-units.sh status` показывает режим bai у stack/backup/backup-verify; в `rollback.sh` стоит
`bai-units.sh revert`; пути в юнитах healthwatch, maintenance, cert-expiry, telemetry-probe и
container-metrics исправлены до удаления старого дерева».

Ключ проверки подписанного манифеста `platform/` задаётся `BAI_PUBKEY`, иначе берётся из каталога
состояния (`cosign.pub`), иначе из установленной платформы; закрепляется один раз командой
`bai pin-key`.
