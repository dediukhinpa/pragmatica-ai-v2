# Чек-лист владельца: переключение боя Прагматики на v2 (шлюз G7)

Красная зона: запускает владелец, на `pragmatika-ru`. Пакет (`cutover.sh`, `rollback.sh`) проверен
на синтетическом бое на Fornex, на самом бое не запускался. Репетиция 7r прошла 14.11 (33 ok /
3 warn / 0 fail); три её предупреждения закрываются шагами ниже.

Окно работ: бой не отвечает от остановки `app` до зелёного `/ready` v2, то есть бэкап (дамп БД
2,2 ГиБ ≈ 2 минуты, `backup.sh --verify` дольше) плюс запуск стека. Назначать окно с запасом
(1–2 часа), в нерабочее время.

## 1. До запуска (за день)

- [ ] **Заморозка G5 держится:** в `pavelded/pragmatica-ai` ничего не сливается до конца G7 и 8r.
- [ ] **Пакет цел:** на Fornex `(cd package && sha256sum -c --quiet MANIFEST.sha256)`; на боевом
      хосте после копирования то же самое (`cutover.sh` проверяет сам).
- [ ] **Подписи образов** (предусловие этапа 8: подписаны ВСЕ digest). На Fornex, где есть `cosign`
      и вход в реестр pull-ключом (временный `DOCKER_CONFIG`, после — `docker logout`):
      `bash verify-signatures.sh --lock images.lock --pubkey cosign.pub --out signatures.txt`.
      Файл `signatures.txt` положить рядом с пакетом на бою. `cutover.sh` сверяет его с `images.lock`
      и отказывается, если подтверждения нет (если на боевом хосте есть `cosign`, он проверит сам).
- [ ] **Образы на хосте:** либо доступ с РФ к `cr.yandex` (вход pull-ключом), либо архив
      `--images-tar` (`docker save` образов `images.lock`). Digest не меняется: образы те же, что
      прошли репетицию 7r (app `sha256:926db237…`). Если digest изменился — нужна новая репетиция.
- [ ] **Диск и память:** `cutover.sh` считает сам (дамп ×3 + запас); свободного места в
      `~/backups` и в каталоге docker нужно не меньше, чем он напишет в отказе.
- [ ] **Старый `backup.sh` работает** (нужны `age`, `rclone`, S3): ночной бэкап последних суток
      прошёл без ошибок. `cutover.sh` вызывает его же с `--verify`; при ошибке бой не меняется.
- [ ] **Боевой `.env`, не пример.** `cutover.sh` берёт `/opt/pragmatika/deploy/.env` и проверяет:
      `ACCESS_POLICY_HOST_DIR=/opt/pragmatika/local/access`,
      `TEMPLATES_HOST_DIR=/opt/pragmatika/local/templates`,
      `DOCUMENTS_HOST_DIR=/srv/pragmatika/documents`, `MAIL_HOST_DIR=/etc/pragmatika/mail`,
      `ACCESS_POLICY_FILE=/etc/pragmatika/access/access-policy.json` (`LOCAL_HOST_DIR` по умолчанию
      `/opt/pragmatika/local`). Значения из `.env.example` (`/etc/pragmatika/access`) на бою неверны.
- [ ] **Права файлов (uid app 1000 / группа 10001).** Файл правил и его каталог читаются uid 1000
      (рекомендуется `root:1000`, 0640 и 0750; цель симлинка внутри смонтированного каталога);
      `mailboxes.json` 0600/0640, владелец 1000 или root. Тома `intake-data`, `file-spool`,
      `documents-exchange` пишутся uid 1000 (образ v2 не создаёт `/var/lib/pragmatika/*`).
      `cutover.sh --preflight-only` проверяет это из контейнера app и ничего не меняет — запустить
      им заранее: `bash cutover.sh --preflight-only --signatures-verified signatures.txt`.
- [ ] **Имена окружения.** `cutover.sh` сам не переносит в `.env` v2: `PRICES_UNVERIFIED_SENDER_POLICY`,
      `SITE_PUBLISH_ENABLED` (код их не читает), `SPEECH_MODEL_REPO`, `SPEECH_MODEL_REVISION`
      (в 1.0.1 читается `SPEECH_MODEL_NAME`). Боевой `.env` остаётся нетронутым: он нужен откату.
- [ ] **Решения, принятые владельцем 13.11 (учтены в пакете, ничего делать не нужно):** образ app
      `1.0.1-pragmatika` ставится как есть (trivy: CRITICAL 0, HIGH 47); поворот/OSD фото остаётся
      выключенным (`DOCUMENTS_IMAGE_TEXT_DETECT_ROTATION=false`, значение compose v2); отличия
      поведения после замены обходов (7u) приняты; метрика выбора менеджера (G-18) **не включать**,
      это отдельная задача после G7.
- [ ] **Три юнита старого дерева** (`pragmatika-cert-expiry`, `pragmatika-telemetry-probe`,
      `pragmatika-container-metrics`): `cutover.sh` их не трогает. До переключения прочитать, что
      с ними делать: `bash units-old-tree.sh` (только чтение: `systemctl cat`, ссылки на
      `/opt/pragmatika`, diff замены на `/opt/pragmatika-v2` там, где цель есть в новом дереве).
      Скрипты хоста (`deploy/scripts/*.sh`: бэкап, обслуживание, метрики, проверка сертификата)
      в v2 **не входят**: они остаются в старом дереве, и его **нельзя удалять**. Отключать юнит
      можно только после подтверждённой замены (метрики идут — см. п. 4), поэтому по умолчанию:
      оставить как есть.
- [ ] **Роли и пароли кластера боя.** При `cutover.sh` каталог данных Postgres (`pgdata`) остаётся
      на месте, поэтому роли (`pragmatika`, `pragmatika_monitor`), их атрибуты, пароли и права
      сохраняются сами. Перенос ролей отдельным шагом нужен только при восстановлении в **чистый**
      кластер (не наш случай, `rollback.sh --restore-db` восстанавливает в тот же кластер).
- [ ] **Решить** (владелец): сколько хранить откат (раздел 6) и кто следит за окном.

## 2. Запуск

```bash
cd ~/pragmatika-cutover-package            # каталог пакета на pragmatika-ru
bash cutover.sh --preflight-only --signatures-verified signatures.txt   # ничего не меняет
bash cutover.sh --signatures-verified signatures.txt [--images-tar images.tar]
```

Параметры: `--soak-seconds N` (выдержка после запуска, по умолчанию 600), `--expected-bots N`
(по умолчанию 4), `--config ФАЙЛ`, `--out-dir КАТАЛОГ`. В ходе скрипт пишет журнал на экран и в
`~/.pragmatika-cutover/run-<время>/results/cutover.log`.

Коды выхода: `0` — переключено и проверено; `1` — сбой, **откат уже выполнен**, бой на прежних
образах; `3` — отказ по предусловиям, бой не тронут; `4` — сбой и откат не удался (раздел 5).

В конце: архив `~/cutover-<время>.tgz` (журнал, проверки, digest, без секретов и данных) —
**вернуть в `stage-8/results/`**.

## 3. Живые проверки после (вручную, сразу)

`cutover.sh` проверяет сам: `/ready` 200, `bitrix24_bot_ready` (ботов не меньше 4), журнал app без
ошибок, образы запущенных контейнеров = `images.lock`, почта как до переключения (состояние, число
ящиков 7, `authBlocked 0`), метрики (`.prom` обновляются), выдержка 10 минут без перезапусков.
Вручную (каналы, почта и реальный шлюз моделей в репетиции не поднимались):

- [ ] Сообщение **в каждого из 4 ботов** в Bitrix24: бот отвечает (реакция и ответ).
- [ ] **Файл:** отправить боту файл (прайс или документ): принят, разобран, ответ пришёл.
- [ ] **Кнопка:** нажать кнопку в приветствии/ответе: команда выполняется.
- [ ] **Поиск:** запрос поиска по прайсам или базе знаний возвращает результат (проверяет схему
      знаний после миграции 026).
- [ ] **Отправка почты выключена, как была:** `EMPLOYEE_MAIL_SEND_ENABLED=false` (письма сотрудникам
      по кнопке не уходят); `/ready` → `mail.state` не `unconfigured`.
- [ ] **Мониторинг:** алерты молчат 10 минут после запуска (если задан `CUTOVER_ALERTS_URL`, скрипт
      считает активные алерты сам); дашборды получают метрики (`docker compose` v2 стек не менял
      `alloy` и телеметрию: контейнеры те же имена); панель расходов не пустая.
- [ ] **Три юнита** (п. 1): метрики контейнеров и проверка сертификата продолжают писать файлы
      (`TEXTFILE_METRICS_DIR`, `.prom` с новой датой). Если юнит ссылался на старое дерево и перестал
      работать — переписать путь по diff из `units-old-tree.sh`, **предварительно** сохранив копию
      юнита (команды в блоке «Откат» вывода скрипта).
- [ ] Ночной `backup.sh` ближайшей ночью прошёл: он работает через прежний compose и находит
      контейнеры v2 по имени проекта и сервиса (`pragmatika`, `postgres`, `pseudonymizer`).

## 4. Если что-то не так

- **Сбой в ходе `cutover.sh`** → откат запускается сам (код 1). Журнал: `rollback.log` в архиве.
- **Проблема выявлена позже** (живые проверки, пользователи): откат вручную —
  `bash rollback.sh` (прежние образы, обратная миграция 026, схема как до v2; данные,
  записанные после переключения, **сохраняются**: миграция 026 только переименовывает столбец и
  возвращает функции поиска).
- **Крайний случай** — `bash rollback.sh --restore-db --i-understand-data-loss`: БД и хранилище
  псевдонимизатора возвращаются на момент **до переключения**. **Всё, что записано после, отрезается**
  от рабочей базы (БД после v2 переименовывается в `<БД>_after_v2_<время>` и лежит до ручного
  удаления; том псевдонимизатора — архив `pseudonymizer-data-after-v2.tgz` в каталоге бэкапа).
  Применять, только если обратная миграция не помогла.
- **Откат юнитов старого дерева** (если правили по п. 1): вернуть сохранённые копии
  `/etc/systemd/system/pragmatika-*.service` из `~/backups/cutover-units-<время>/`,
  `sudo systemctl daemon-reload`, `sudo systemctl restart <юнит>`.
- **Код 4** (откат не удался): бой может быть остановлен. Порядок: прочитать конец `rollback.log`;
  поднять прежний стек вручную (`bash /opt/pragmatika/deploy/scripts/dc.sh up -d`), при
  необходимости `bash rollback.sh` ещё раз (идемпотентен); данные и бэкапы целы (каталог
  `~/backups/pragmatika-before-v2-<время>`).

## 5. Что лежит после

| Что | Где |
|---|---|
| Бэкап до переключения | `~/backups/pragmatika-before-v2-<время>/` (`db.dump`, архив `/opt/pragmatika` без `local/`, архив тома псевдонимизатора, `.env` и `secrets.env` (600), списки контейнеров и образов); штатный архив `backup.sh` (`.tar.age`) в S3 |
| Прежние образы | локально, `cutover.sh` их не удаляет; `docker image prune` не запускать, пока хранится откат |
| Прежнее дерево | `/opt/pragmatika` без изменений (скрипты хоста, compose, `local/`) |
| Новое дерево | `/opt/pragmatika-v2/{deploy,db}`; `.env` v2 (600), ссылка на `secrets.env` |
| Журнал запуска | `~/.pragmatika-cutover/run-<время>/` и архив `~/cutover-<время>.tgz` |

## 6. Сколько хранить откат (решение владельца, план п. 7)

Рекомендация координатора, владелец может изменить:

- **Быстрый откат** (образы + `rollback.sh`) безопасен, пока в БД не появилось ничего, чего не
  понимает старый код: то есть **до первой новой миграции после переключения** (выпуск платформы
  1.0.2, функции этапов 9–11) и до первого изменения в данных, которое пишет только v2. После
  этого откат — только `--restore-db` с потерей данных.
- **Срок:** не менее **14 суток** после снятия заморозки (две недели рабочих циклов: прайсы,
  ночные бэкапы, месячное закрытие) и не дольше первой миграции после G7. Первым событием из двух.
- Хранить всё время отката: прежние образы, `/opt/pragmatika` целиком, бэкап
  `~/backups/pragmatika-before-v2-*` (≈ дамп БД ×1 + архивы).
- По истечении срока (решение владельца): удалить прежние образы (`docker image rm` по списку из
  `images-before.tsv`), вынести три юнита на новое дерево и только затем рассматривать удаление
  `/opt/pragmatika` (скрипты хоста бэкапа и обслуживания переносятся в v2 отдельной задачей).

## 7. Когда снимать заморозку

Заморозка (G5) снимается после проверки **8r** по архиву `stage-8/results/` и живым проверкам
раздела 3: `cutover.sh` код 0, 10 минут без алертов, боты отвечают, файл/кнопка/поиск работают.
Разработка после этого идёт только в v2 (`dediukhinpa/pragmatica-ai-v2`), в старый репозиторий
не сливается. Если выполнен откат, заморозка **не** снимается.
